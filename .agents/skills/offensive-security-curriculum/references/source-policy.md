# Source and Research Policy

## Source priority

1. Current official standards, specifications, and project documentation.
2. Vendor documentation for the product or platform being described.
3. Primary security research, advisories, papers, and maintainer repositories.
4. Established training material for pedagogy and external lab mapping.
5. Community articles only when they add a clearly attributed perspective.

Search the web for claims that may have changed, including framework versions,
platform behavior, project maintenance, repository setup, certification curricula,
policies, standards, and vulnerability details.

## External lab candidates

- OWASP Juice Shop: <https://github.com/juice-shop/juice-shop>
- GOAD: <https://github.com/Orange-Cyberdefense/GOAD>
- CloudGoat: <https://github.com/RhinoSecurityLabs/cloudgoat>
- Atomic Red Team: <https://github.com/redcanaryco/atomic-red-team>
- MITRE CALDERA: <https://github.com/mitre/caldera>

Before adopting one, verify its current maintenance state, license, architecture,
resource cost, supported platforms, warnings, isolation requirements, and cleanup.

## Citation quality

- Cite the exact page supporting the claim, not a search-result page.
- Do not cite a repository star count as evidence of technical quality.
- Do not use a certification outline as the sole authority for a technical claim.
- Distinguish sourced fact, pedagogical recommendation, and inference.
- Preserve publication/update/access dates for time-sensitive material.
- Do not copy long passages, lab solutions, diagrams, or proprietary course content.
- Recreate explanations in original language and link learners to the source.

## Vulnerability content

For a real vulnerability, prefer the vendor advisory, CVE record, CWE class,
maintainer patch/commit, and primary researcher write-up. State affected versions,
preconditions, impact, patch status, and disclosure timeline only when sourced.
